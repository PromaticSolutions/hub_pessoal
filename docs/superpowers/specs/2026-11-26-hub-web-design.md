# Personal Task Hub Web — Design

Data: 2026-11-26 · Status: aprovado pelo usuário (2026-11-26, "faz po, tem que deixar pronto para rodar em produção")
Base: app v2 desktop (branch `main` = `feat/hub-v2`, schema SQLite v7). Specs anteriores continuam valendo para regras de negócio.

> **[decisão do Claude]** = preenchido por mim, não pedido explicitamente.

## 1. Intenção

O usuário trabalha em **dois notebooks** e quer o hub com os mesmos dados nos dois. Escolheu o caminho A: virar site (Vercel + Supabase). As telas, regras e funcionalidades continuam as mesmas; muda só por onde os dados passam. Os dados já cadastrados no app desktop têm de ir para o Supabase **sem perda**, conferidos por contagem.

## 2. Objetivos

1. Mesmo app (todas as telas e regras da v2) rodando no navegador, hospedado na Vercel, pronto para produção.
2. Dados no Supabase (Postgres) e arquivos (anexos, logos) no Supabase Storage.
3. Login (email + senha), só o usuário.
4. Importação única do `hub.db` local + anexos/logos, com conferência de contagens; nada é alterado no lado local.
5. Instalável como app pelo Chrome nos dois notebooks (ícone próprio).

## 3. Não-objetivos / anti-objetivos

- Não reescrever telas nem mudar regras (mesmos métodos, mesmas validações, mesmos `data-testid`).
- Não funcionar offline (aceito pelo usuário).
- "Mostrar na pasta" deixa de existir; "abrir anexo" passa a abrir/baixar pelo navegador (aceito pelo usuário).
- **Anti-objetivo:** qualquer perda ou divergência de dados na importação. Se uma contagem não bater, a importação falha e nada segue.
- **Anti-objetivo:** dados acessíveis sem login (chave anon do Supabase não pode ler nada).

## 4. Restrições

- Supabase: projeto `hub_pessoal` (ref `syutpdhqwrlusgjprbld`, sa-east-1, org PromaticSolutions). Plano grátis: pausa após 7 dias sem uso (usuário avisado). Conexão IPv4 só pelo pooler `aws-0-sa-east-1.pooler.supabase.com` (6543 transação para a API; 5432 sessão para migração/importação).
- Segredos só em `.env.local` (ignorado pelo git) e nas variáveis da Vercel.
- Vercel: funções serverless com limite de 4,5 MB de corpo → uploads vão direto ao Storage por URL assinada.
- O app desktop instalado e o `~/.local/share/personal-task-hub` continuam intactos.

## 5. Abordagens consideradas

- **A) Site Vercel + Supabase (escolhida pelo usuário).** Mesmas telas; servidor vira API; dados no Postgres. Perde offline; ganha qualquer dispositivo.
- B) App desktop nos dois notebooks usando o mesmo banco online. Mesmo trabalho de reescrita, ainda exige internet e instalar/atualizar em cada máquina.
- C) Tudo local + sincronização. Funciona offline, mas conflitos ao editar nos dois lados; maior risco de perda — contra a regra principal.

## 6. Arquitetura

```
navegador (React SPA, mesmo src/renderer)
   │  POST /api/rpc {method, input}  + Authorization: Bearer <jwt Supabase>
   ▼
Vercel Function api/rpc.ts ──► dispatch(handlers) ──► services (async) ──► Db (postgres.js, pooler 6543)
   │                                                     └──► Storage (Supabase Storage, bucket privado)
   ▼
Vercel Cron api/cron/daily.ts → backup JSON diário + limpeza de anexos excluídos
```

- **Mesma API:** os 128 métodos de `handlers.ts` continuam com os mesmos nomes, entradas (zod) e saídas (`ApiMethods`). O `api()` do renderer troca IPC por `fetch`. **[decisão do Claude]**
- **Camada Db** (`src/server/db`): interface `Db` com `one / many / run / exec / tx`; placeholders `?` convertidos para `$n`. Duas implementações: postgres.js (produção) e PGlite (testes e dev local). `count`/`bigint`/`numeric` voltam como `number`. **[decisão do Claude]**
- **Esquema Postgres** no schema `public` (o pooler em modo transação não garante `search_path` customizado), RLS ligado em todas as tabelas sem políticas, `revoke all` de `anon`/`authenticated` nas tabelas, sequências, view e funções (e `alter default privileges`), de modo que a chave anon não lê nada. Mesmas tabelas/colunas/ids da v7. Datas continuam **texto ISO** como hoje (evita mudar regras de data). Booleanos continuam inteiros 0/1. `position` em `double precision`. Ids `integer generated by default as identity` (importação preserva ids e acerta as sequências). **[decisão do Claude]**
- **Busca:** tabela `search_index(entity_type, entity_id, title, body, norm)` mantida por gatilhos (como o FTS5 hoje); `norm` = texto minúsculo sem acentos (função `norm_text` imutável com `translate`). Cada palavra digitada vira `norm LIKE '%palavra%'` (todas obrigatórias); ordem: acerto no título primeiro; trecho `«…»` gerado em JS. Mesmos tipos de resultado de hoje. **[decisão do Claude]**
- **Fuso horário:** servidor fixa `process.env.TZ = APP_TZ` (padrão `America/Sao_Paulo`) antes de qualquer cálculo, para "hoje", "atrasada", semana e Meu Dia baterem com o app atual. SQL com `date('now','localtime')` passa a receber a data calculada em JS. **[decisão do Claude]**
- **Arquivos:** bucket privado `hub-files`: `attachments/<stored_path>`, `logos/<arquivo>`, `deleted/…` (lixeira 30 dias, como `attachments-deleted`), `backups/auto/…`, `uploads/tmp/…`. Interface `Storage` com implementação Supabase (produção) e disco local (dev/testes).
  - Upload: `files.uploadUrl` → URL assinada → navegador envia o arquivo → `attachments.add` / `companies.setLogo` com as chaves enviadas.
  - Abrir/baixar: `attachments.url` → URL assinada (1 h) → nova aba. Miniaturas e logos: URL assinada.
- **Login:** Supabase Auth email+senha via `@supabase/supabase-js` no navegador; sessão persistida pelo SDK. A API valida o JWT (JWKS do projeto, cache) e exige o email em `ALLOWED_EMAIL`. Cadastro público desligado. **[decisão do Claude]**
- **Backup/restauração:** "Baixar backup" gera JSON com todas as tabelas (+ versão do esquema e contagens). Restaurar: envia o JSON ao Storage → servidor valida → backup automático antes → substitui tudo numa transação. Backups automáticos: cron diário grava em `backups/auto/`, mantém 30; lista e "restaurar este" continuam. Arquivos dos anexos ficam no Storage (não entram no JSON). **[decisão do Claude]**
- **Dev local:** `npm run dev` = Vite com middleware `/api/rpc` usando PGlite em arquivo (`.data/`) e Storage em disco; login dispensado **só** quando `HUB_DEV_AUTH=1` e não está em produção. Produção nunca usa PGlite nem bypass (checado na inicialização). **[decisão do Claude]**

## 7. Adaptações de tela (o mínimo)

- Tela de login (quando não há sessão) e "Sair" em Configurações.
- Seleção de arquivos: `<input type=file>` e arrastar-soltar com `File` (sem caminhos locais).
- "Mostrar na pasta" e "Abrir pasta de dados" removidos; "Abrir" abre em nova aba.
- Configurações → Backup: baixar JSON / restaurar de arquivo / lista de automáticos; "Dados" mostra contagens e uso do Storage em vez de caminho local.
- Salvar ao sair: `visibilitychange`/`pagehide` disparam `flushAll` (substitui o flush do Electron).
- Atualização entre notebooks: `refetchOnWindowFocus` ligado — ao voltar para a janela, os dados da outra máquina aparecem.
- Estado das abas (`tabs.state`) guardado no navegador (`localStorage`) por dispositivo, para os dois notebooks não brigarem. **[decisão do Claude]**
- Atalhos: navegadores não deixam interceptar Ctrl+T/Ctrl+W/Ctrl+Tab. Mantém os de hoje onde funcionarem e adiciona **Alt+T** (nova aba), **Alt+W** (fechar), **Alt+1…9** (ir para aba), **Alt+PageDown/PageUp** (próxima/anterior). **[decisão do Claude]**
- PWA: `manifest.webmanifest` + ícones → "Instalar app" no Chrome.

## 8. Importação dos dados

Script `scripts/import-sqlite.ts` (rodado por mim, uma vez):
1. Copia o `hub.db` para um arquivo temporário com `VACUUM INTO` (só leitura no original).
2. Recusa se o banco de destino já tiver dados (a menos que `--replace`).
3. Insere todas as tabelas preservando ids, numa transação; acerta sequências; reconstrói o índice de busca.
4. Envia anexos e logos ao Storage nos mesmos caminhos relativos.
5. Confere: contagem por tabela igual nos dois lados, soma de verificação (md5 de id+campos principais ordenados) para tarefas, projetos, comentários, ideias, compras; arquivos: quantidade e tamanhos. Mostra o relatório; qualquer diferença = falha.
